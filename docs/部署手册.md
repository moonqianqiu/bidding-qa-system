# 部署手册

> 适用：本机开发/单机部署（Windows，绿色安装路线）。容器编排为可选演进，不在本期。
> 本文是**运维唯一入口**：安装/启停/数据初始化/验收命令/运维日历/排障坑表都在这里。

## 1. 首次安装

```bash
# 1) 依赖：Python 3.14 + Node 22 + uv
# 2) 绿色数据服务（zip 落 services/，数据在 data/db/，删目录=彻底卸载）
bash deploy/download-services.sh     # 分段并行下载（走 PDL_PROXY 可选）
bash deploy/install-services.sh      # 幂等解压 + initdb + Neo4j 初始密码 bidqa_dev_2026

# 3) 后端
cd backend
uv sync
cp .env.example .env                 # 填三槽位（CHAT_*/EMBEDDING_*/JUDGE_*）见 docs/01 §5；图片双通道另配 OCR_*（能力型，可不填）

# 4) 前端
cd ../frontend && npm install
```

## 2. 启停与状态

```bash
bash deploy/start.sh    # PostgreSQL → Qdrant → Neo4j → backend(uvicorn workers=1，写死)
bash deploy/status.sh   # 端口+pid属主+HTTP 表；「存活但未持有」=陈旧记录（旧代码还在跑的信号）
bash deploy/stop.sh     # 逆序停机（属主校验后杀）+ 残留检测；NIGHT-028 起停机序列在隔离 worker 执行（真控制台 CTRL_BREAK 广播会波及脚本自身），壳进程 python waiter 有界等待（上限 240s），全程日志 data/run/stop-<时间戳>.log；--force 跳过优雅投递直接强停；完成判定以日志末尾 STOP-DONE + status.sh 为准
```

- **workers=1 是硬性约定**（限流/在线评测/日志缓冲/压缩缓存均进程内状态）：由 `cli/serve.py` 写死（start.sh 经 `bidqa serve` 启动）；`WEB_CONCURRENCY` 会被 uvicorn 忽略，设多值仅启动告警、不拒绝启动（审计 P1-29）。**勿直接** `uvicorn bidqa.main:app --workers N` 绕过入口。
- **pid 文件 = 真实监听者的 Windows pid**（start.sh 由 `netstat -ano` 端口归属取得）。
  stop 前做属主校验：pid 必须仍持有对应端口才杀，陈旧记录拒杀不误杀；存活检测走 `ps -W`（无特权），
  taskkill 被环境拦截时 PowerShell `Stop-Process` 兜底。
- PG 需 `SeCreateGlobalPrivilege`（本项目已一次性授权；重装系统后重跑
  `deploy/diagnosis/grant-createglobal.ps1`）；管理员账户下由 start.sh 预置 `PG_RESTRICT_EXEC=1` 跳过自降权。
- Neo4j 必须配微软 JDK21（`services/jdk21`，start.sh 自动探测）。
- 端口：后端 8000 / 前端 dev 3000 / PG 5432 / Qdrant 6333 / Neo4j 7474+7687。
- **优雅停机与停机演练**（P1-8，2026-11-21）：SSE 广播（error 5031）主投递点在 `cli/serve.BidqaServer.shutdown()` 入口——**先 `broadcast_shutdown()` 再 super()**（uvicorn 0.54 停机时序是「先等连接收尾/超时 cancel、之后才跑 lifespan」，lifespan 内的广播必然空投；`main.py` 停机四步保留兜底，口径见 docs/01 §6）。演练入口：`data/run/drill_shutdown.py`（**进程内信号路径**，检查 SSE 广播/无残留/重启六组件/数据面计数不变）——2026-11-21 演练②③④全 PASS、①已收口（信号后 0.13s 收到 error 5031、干净 EOF、退出码 3=uvicorn 重放 SIGBREAK 的环境默认）；Git Bash PTY 下 os.kill/广播式优雅信号不可达（进程内信号正常）；**NIGHT-013 起 `deploy/stop.sh` 默认优雅先行**（定向 CTRL_BREAK → 30s 超时强停兜底，PTY 下实测送达、后端优雅停机序列完整；`--force` 保留旧强停路径）。真控制台（原生 cmd/PowerShell）复验仍建议由用户执行。
- **NIGHT-028 起停机序列整体移入隔离 worker（双进程架构）**：真控制台下「脚本与服务同控制台」时，定向 CTRL_BREAK 实证为**整控制台广播**（backend_pid 并非 Windows 进程组 id）——backend 优雅四步照常完成，但脚本 bash 自身被击杀（不可 trap 保护）、neo4j.bat 包装 cmd 弹「终止批处理操作吗(Y/N)?」永久等待、Neo4j JVM 仅打线程转储幸存。现架构：**壳进程**（用户控制台）只做预检 → 以隐藏控制台启动脱离 **worker**（不在任何服务控制台内，CTRL_BREAK 投递照常可达）→ `exec python waiter` 有界跟踪 worker 日志（上限 240s，实时回显进度；worker 提前消失时提前返回不死等）；worker 执行原四段停机序列 + 每步硬超时 + 残留清扫（Neo4j JVM 按 services 下 java.exe 路径匹配强停、Y-N 包装 cmd 按「cmd.exe 且命令行含 neo4j」匹配强停），全程写 `data/run/stop-<时间戳>.log`，末尾 `STOP-DONE rc=0` 为完成标记。`--force` 跳过优雅投递按旧强停路径执行。
- **stop.sh 排障口诀：输出中断 ≠ 停机失败**——①`tail data/run/stop-<最新时间戳>.log`，末尾有 `STOP-DONE rc=0` 即停机序列已完成；②`bash deploy/status.sh` 确认五端口释放；③控制台若见 Y/N 提示按 Y 即可；④日志中断但服务仍在 = 广播波及可见进程，直接重跑 `stop.sh`（幂等）；⑤worker 日志缺失 = worker 启动失败（按脚本提示改在 Git Bash 运行）。

## 3. 数据初始化

```bash
cd backend
uv run bidqa ingest knowledge --input <FAQ.xlsx>            # 知识库（嵌入+双稀疏；--dry-run 抽样含 url= 段——付费嵌入前人工核验来源 URL 映射，无 URL 列/值非法时显示为空）
uv run bidqa ingest db --input <业务.xlsx> --sheet Sheet2    # 业务库（金额/地区归一）
uv run bidqa ingest graph --batch-id sample --clear          # 图谱（约束先行；无映射参数=恒等映射，零模型调用）
uv run bidqa ingest graph --batch-id default --normalize --dry-run   # 实体归一预览（默认 SUBJECT_BATCH_* 批量通道；落盘 mapping JSON+复核 CSV，不动图谱）
uv run bidqa ingest graph --batch-id default --normalize --normalize-channel chat --dry-run  # 改走主模型槽位
uv run bidqa ingest graph --batch-id default --mapping-file data/processed/graph_alias_mapping_default.json --clear  # 用复核后的映射重建（零模型调用）
uv run bidqa ingest pdf --input <法规.pdf> --source-type 法规 --title <标题>   # PDF/法规/招标文件（F2/F3/F4，先加 --dry-run 预览）
uv run bidqa ingest pdf --input <法规.txt> --source-type 法规 --title "标题（文号）" --batch-id reg-20261121 --url <来源URL>   # .txt 直入（法规采集产物复用 pdf 切分契约，c7e0590；自动剥【语料元数据】/「键：值」头部、整篇记 page:1）；试运行加 --dry-run（不写库/不调嵌入）
uv run bidqa doctor                                          # 体检：配置/连通/槽位/source_type 分布
uv run bidqa user add <名> --role user [--password]           # 建号（缺省交互输口令；首次调用自动建表+种子管理员）
uv run bidqa user reset <名> [--password]                     # 重置口令（admin/admin123 默认口令改密用这条；改密即吊销该用户全部会话）
uv run bidqa user disable <名>                                # 停用（其会话即刻失效）；enable 反之
uv run bidqa user list                                        # 列出用户
```

> **用户管理 / 游客开关 / 全库会话清理已有 GUI**（2026-11-09）：admin 登录 → 侧栏「▦ 控制台」（`/console`），
> 建号/改密/停用、游客开关、空壳会话清理由界面完成；上表 CLI 保留作脚本通道（语义同款：改密同事务吊销会话、开关即时生效）。

**图谱关系核对**（Neo4j 只读；2026-11-18 起控制台同时报节点与关系计数——KPI「图谱关系」卡取 `relationship_total`）：

```bash
# Neo4j browser（http://127.0.0.1:7474）或 cypher-shell 只读执行：
MATCH ()-[r]->() RETURN type(r), count(*) ORDER BY count(*) DESC   # 五类边计数（FOR/PROCURED/WON/IN 各=项目数，AGENTED 有代理机构的项目数）
MATCH (p:Project)-[r]->(x) RETURN p,r,x LIMIT 25                   # 抽样看边的两端实体
```

**标的物批量提取**（F6 数据修复：PG 8,489 行 subject_matter 全 NULL → 免费档 GLM-4.7-Flash 同步并发回填）：

```bash
uv run bidqa subject-batch build   # 拉去重项目名 → requests.jsonl + names.json（--dry-run 只打印）
uv run bidqa subject-batch run     # 同步并发执行（需 .env 配 SUBJECT_BATCH_API_KEY；断点续跑，--workers 调并发）
uv run bidqa subject-batch fetch   # 解析 → subject_map.json（默认试运行；--write 才写回 PG）
```

国际版 z.ai 无 Batch API（openapi.json 核实），故为同步并发直调 chat/completions；
结果行增量落盘可断点续跑，失败条目已记行（重跑 run 跳过已落盘项，要重试失败项先删对应行）。
统一试运行约定：以上命令均支持 `--dry-run`（打印条数+抽样5条+不写库）。

## 5. 运维日历与数据资产

**节奏**：
- 每次开机：`bash deploy/start.sh` + 前端 `npm run dev`
- 改了语料/数据：重新 ingest → **必查检索三路**（`eval smoke`，hit_rate 应 1.0）；`ctx_summary` 空摘要合法入库（F3 诚实降级），查库里 source_type 覆盖度用 `uv run bidqa doctor`（取不到记「不可用」）
- 每周（决策 #8）：人工巡检 SiliconFlow/SenseNova/判分中转控制台额度（>60% 冻结批量操作）；
  `prune --days 30 --dry-run` 看看数据量
- 发版前：DoD 清单（docs/03 §0.1）→ pytest/tsc/e2e/eval 全绿 → 打 tag

## 6. 排障坑表（症状 → 动作，按踩坑次数排序）

### 服务与部署

| 症状 | 处置 |
|---|---|
| PG/服务成批 `0xC0000142 STATUS_DLL_INIT_FAILED` | 沙盒会话进程树被系统加固拦截：**让用户在自己终端跑 `deploy/start.sh`**，或命令加 `dangerouslyDisableSandbox` |
| PG initdb 报 1314 | 授 SeCreateGlobalPrivilege（`deploy/diagnosis/grant-createglobal.ps1`，重登生效）+ `PG_RESTRICT_EXEC=1` |
| Neo4j 启动报 `UnsatisfiedLinkError: jnidispatch.dll ... 拒绝访问` / `AccessDeniedException: D:\Temp\UserTemp\decompressed-browser*` | 全局临时目录多会话共用，JNA 与 browser 解压遇残留/属主不匹配被拒；`start.sh` 已给 JVM 独立 `-Djava.io.tmpdir` + `-Djna.tmpdir`（2026-11-10 实证修复） |
| Neo4j 起来但不应答 | `deploy/diagnosis/nio-test.cmd`：SELECTOR-DEAF = 系统加固拦截 WEPoll（非项目问题） |
| health 图谱「不可用」但 Neo4j 进程在跑 | 先查端口错位：`netstat -ano \| grep 7687`。`services/neo4j/conf/neo4j.conf` 尾部的定制段若写 7475/7688 会与约定端口（.env/手册/start.sh/config 默认）错位，后端永远连不上（2026-11-08 实证已修回 7474+7687）；次查 `data/run/neo4j.log` 的 `Bolt enabled on` 行确认实际监听口 |
| hosts 有 Typora 条目 | `deploy/diagnosis/fix-hosts-localhost.ps1`（127.0.0.1 localhost 置首） |
| 改了代码没生效、答案还是旧语义 | 已根治（2026-11-07）：pid 文件记真实监听者 + stop 属主校验 + status「存活但未持有」会点名。历史坑：pid 曾记 `uv` 包装进程，真服务是 python 子进程，按 pid 杀不掉 |
| 后端探活 000/拒绝 | `bash deploy/status.sh`；`tail data/run/backend.log` 看日志末尾 |
| status 显示「已死(残留)」 | 残留 pid 文件不是故障，start 前不用手动清 |
| tasklist/taskkill 报「用户名或密码不正确」 | 受控/沙箱会话的系统加固拦截（非项目故障）：启停脚本已内置对策——存活检测走 `ps -W`、停止 taskkill→PowerShell `Stop-Process` 兜底；彻底不行就让用户终端跑 |
| `stop.sh` 输出中断/看似卡住/控制台弹「终止批处理操作吗(Y/N)?」 | NIGHT-028 起实际停机在隐藏控制台 worker 中执行（壳进程 python waiter 有界跟踪 ≤240s）：看 `tail data/run/stop-<时间戳>.log`——末尾 `STOP-DONE rc=0` = 完成，随后 `bash deploy/status.sh` 确认端口释放；Y/N 提示是 neo4j.bat 包装 cmd 收到广播的已知形态，按 Y 即可；残留 Neo4j JVM 已由 worker 按 services 下 java.exe 路径自动清扫；worker 日志缺失 = worker 启动失败，在 Git Bash 重跑 |

### 后端行为

| 症状 | 处置 |
|---|---|
| health `status:degraded` | `/api/health` 的 components 看哪个「不可用」；按槽位查 key/网络。设计就是单点降级不断服 |
| 回答总是「未包含」/ 命中率 0 | dense/sparse 两路是否齐全（dense 缺失坑）→ `eval smoke` 看 hit_rate；低就真实 key 重新 `ingest knowledge`（入库后必查检索 mode 的教训见开发日志 11-02） |
| 来源相关度条消失 / CRAG 每次都改写 | 未配 `RERANK_*` 时 `sources[].score` 为 `null`（RRF 排名分不冒充相关度）属预期：前端不显示相关度条、`quality_note` 不贴标签、CRAG 不触发改写。若配了重排仍无条，查重排分是否为有限数 |
| 上游 429 `inference exceeds tpm/rpm limit` | sensenova 自动退避（≤45s 总预算）；长时间连续 e2e 仍可能耗尽 → 降并发/等额度。**其它端点 429 原样报错，勿加全局重试**（红线见 AGENTS.md） |
| 空白气泡 | 已双层自动处理（2026-11-10）：①llm 空流（200 但 0 chunk）在自建中转端点补发一次；②loop 最终空正文补发一次无工具直答——仍空才下发 `empty_answer` 诚实文案（补发成功记 `empty_answer_retry`，降级面板可见）。排查查 `backend.log` 的「上游流式响应为空」；若诚实文案仍频繁出现，说明上游故障持续，考虑换端点/模型 |
| 多轮工具调用 HTTP 400 `invalid arguments` | 回传 assistant 的 `function.arguments` 必须是 JSON **字符串**（`loop.py`，勿回退） |
| 工具反复报 bad_arguments | 模型传参 vs 工具枚举/白名单。正常现象：工具回错误→模型自纠（看 degraded 记录）；频繁出现就锐化工具描述 |
| 附图发送变慢 / 超大图被拒（413） | v2.3 双通道一次上传两份（预览 1024/0.85 + 原件 2000/0.92），解析发生在点发送时属预期（chip 显示「图片解析中…」）；单字段 base64 > 4M 字符即 413/4131，**反向代理部署需放开 client_max_body_size**；OCR 未配置时自动退化为 Qwen 描述（响应 `degraded=false`、`route_by=unavailable`），手动「按文档解析」才 5031 |

### 前端

| 症状 | 处置 |
|---|---|
| token 全部最后一次性到达 | 是否走了 dev 代理——`lib/sse.ts` 必须直连 `127.0.0.1:8000`（代理会缓冲整个 SSE） |
| 前端 `127.0.0.1:3000` 不通 | `vite.config.ts` 的 `server.host` 固定绑 `127.0.0.1`（Vite 缺省只听 `::1`，勿删）；或改用 `localhost:3000` |

### 命令行与工具链

| 症状 | 处置 |
|---|---|
| `uv run` 报 exe 占用 / lock 拒绝访问 | 有进程持着 venv：先停后端再跑，或加 `--no-sync`；沙盒拦 uv 缓存锁时关沙盒执行 |
| `uv trampoline failed to canonicalize script path` | venv 入口 exe 烧录的是**创建时的绝对路径**——仓库改名/移动后失效。普通 `uv run`（不带 `--no-sync`）触发 sync 即自愈项目自身入口；第三方入口（如 pytest）需 `uv sync --reinstall-package pytest`；彻底重置：删 `backend/.venv` 后 `uv sync` |
| curl 中文 body 400/乱码 | 终端传参坏编码 → 写 UTF-8 临时文件 + `--data-binary @file`（e2e 脚本即此法） |

| backend/ 下出现 jieba.cache / pytest-of-* / tmp* 产物 | 环境缺 TEMP 时 tempfile 兜底到当前目录；conftest 已把临时根钉到系统目录、.gitignore 有兜底规则——若仍出现，设置 TEMP/TMP 后重跑 |
| 跑完 pytest 图谱变空 / PG 冒出 3 行 it-* 数据 | 已根治（2026-11-08）：`test_graph` 模块夹具曾 teardown `clear_all()` **清空真实图谱**、`test_subject_writeback` 收尾不清理留 it-sm 残留（+3 行之谜）；已改前缀 scoped 清理（图谱只删 IT-G* 自建节点、PG it-sm try/finally）——跑完测试 PG/图谱计数不变。历史事故重建：`uv run bidqa ingest graph --batch-id sample --clear`（约 20 分钟；2026-11-14 起默认不调模型走恒等映射，归一是显式 `--normalize` 付费动作） |

## 7. 接 Langfuse / Jaeger（OTel span 导出，WP3）

一次问答的 span 树（`chat.turn` → `agent.round` → `llm.chat_stream` / `tool.<name>`，旁挂 `rag.retrieve` / `persist`）经 OTLP/HTTP 导出，可对接任何 OTLP 兼容后端。**默认关闭**：`OTEL_EXPORTER_OTLP_ENDPOINT` 留空时零开销 no-op（不起线程、不发网络、不改全局 provider）。

```bash
# backend/.env 追加（或直接设环境变量）：
# Jaeger（本机，v1.35+ 内置 OTLP）：
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318
# Langfuse Cloud / 自建（OTLP ingestion，Basic Auth 头走 OTel 标准变量）：
# OTEL_EXPORTER_OTLP_ENDPOINT=https://cloud.langfuse.com/api/public/otel
# OTEL_EXPORTER_OTLP_HEADERS="Authorization=Basic <base64(public_key:secret_key)>"
OTEL_SERVICE_NAME=bidqa
```

- 端点自动补 `/v1/traces`；已写全路径（如 Langfuse 完整 OTLP URL）则原样使用
- 改完 `bash deploy/stop.sh && bash deploy/start.sh` 重启后端即生效；`/api/health` 不探此项
- 导出失败（collector 不在/断网）只影响观测数据上报，**不影响业务问答**（SDK 内部吞错记日志）
- 隐私白名单：span 属性只放长度/工具名/模型名/耗时/rounds/outcome/degraded 等元数据，问题原文、回答正文、密钥绝不入 span（见 docs/01 §6「可观测性 span 埋点」段）
- **FastAPI 原生 HTTP 层 span（2026-11-21 实接验证）**：OTLP 启用后，FastAPI ≥0.162 原生 HTTP 层 span 会**自动附加**——`fastapi.dependencies` / `fastapi.endpoint` / `fastapi.serialization` + 路由 span，属性仅 path/route/status（含 `url.path`）；**端点设计避免敏感 query 参数**（敏感数据不要放 URL query，框架层 span 不受项目隐私白名单管辖）
