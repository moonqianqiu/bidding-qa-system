## 1. 结论摘要

**现状选型保留**（Qdrant + BAAI/bge-m3 + bge-reranker-v2-m3），三条理由：

1. **结构性事实：候选中只有 bge-m3 一次调用同时返回稠密 + 学习型稀疏向量**（已核实来源：
   [HF 模型卡](https://huggingface.co/BAAI/bge-m3)、[arXiv 2402.03216](https://arxiv.org/html/2402.03216v3)）。
   换任何其它候选（Qwen3-Embedding / gte-Qwen2 / jina-v3 / OpenAI）都会丢掉学习型稀疏通道，
   hybrid 两路退化为「dense + jieba 纯词频 BM25」——这不是纯 embedding 替换，而是链路形态变化。
   （2026-11-22 NIGHT-040 实测注记：SiliconFlow `/embeddings` 公开端点暂不返回 `sparse_embedding`——
   学习型稀疏仅在提供商返回时参与，见 `docs/01` §4.1 口径债；本条选型结论不变。
   **2026-11-23 NIGHT-065 更新**：自建 bge-m3 端点（SLali L20）已交付 `sparse_embedding`，
   三路向量全量写入、hybrid 恢复两路 RRF——选型结论（bge-m3 唯一同时给稠密+学习型稀疏）由此实测证实。）
2. **链路围绕现选型建成**：三路 Named Vectors（schema 声明，实际写 dense+sparse_bm25 两路）+
   客户端 RRF k 注入（`FusionQuery` 固定 k=2 的勘误
   已落地为两路独立查询 + `database/rrf.py` 客户端融合）+ 双写灾备（决策 #4）都是围绕 Qdrant +
   bge-m3 双路输出设计的；迁移 = 重写检索层 + 全量重 ingest + 评测重跑，当前没有任何压力要求付这笔成本。
3. **规模远未到分界线**：当前 75 向量（见 §1.1 实测），规划语料（3-5 部法规全文 + FAQ + 招标文件
   解析文本，决策 #12）预估万级块——低于任何候选向量库的能力分界（§3）。

**必须待实测才能定的**（全部等真实语料 + 付费跑批，本轮只给协议与口径，见 §4/§5）：
RRF k 分档值（30/60/90 是拍定值非调优值）、rerank 候选池大小、CRAG 阈值 0.35 是否随语料漂移、
chunk 兜底切分 500 字粗细、BM25 通道开 IDF 的收益。**在语料到位前（当前 75 向量、且为旧编码口径），
任何候选对比结论都不成立、不外推**（`eval/retrieval_eval.py` 的 `CORPUS_NOTE` 已随快照落档同一声明）。

**结构性结论（对评测协议的约束）**：
- 候选中**只有 bge-m3 提供原生学习型稀疏**。若评测 Qwen3/gte/jina/OpenAI 任一候选，
  `sparse` 通道无模型侧输入，hybrid 实际变成「dense + sparse_bm25（jieba 纯词频）」两路——
  与基线（dense 单路——当前实测常态，见 `docs/01` §4.1）的差异**必须**在对比报告里单列声明，否则结论混淆了两个变量。
- 维度不同（1024/1536/2560/3584）→ 换模型必然**新集合重 ingest**（`docs/01` §4.1 版本化集合，
  禁原地重建）；即使维度恰好相同（bge-m3 与 Qwen3-0.6B 同为 1024）也**禁止**复用旧向量——
  语义空间不同，混用等同数据污染。
- jina-v3 许可为**非商用**（CC-BY-NC）：本项目验收含甲方验收，非商用权重许可即出局，
  除非走 Jina API（商用条款）。已列入 §6 风险。
- gte-Qwen2-7B 与自托管路线在「决策 #2：本地零 GPU 零模型」约束下当前**不可行**，
  仅作语料规模升级后的备选记录。

## 3. 向量库候选对比

现状事实：Qdrant 单机**绿色安装**（`services/` 官方 zip，删目录=彻底卸载，拷问决策 #1），
集合 `bidqa_knowledge_v1` schema 声明三路 Named Vectors（dense COSINE 1024 / sparse / sparse_bm25；
实际写 dense+sparse_bm25 两路，docs/01 §4.1 口径债），
payload schema 校验拒收，版本化集合 + 原子切换流程已成文（`docs/01` §4.1）。

| 候选 | 稀疏/hybrid 支持 | 过滤能力 | 运维复杂度 | 规模 | 与现有栈契合度 |
|---|---|---|---|---|---|
| **Qdrant（现状）** | 原生 sparse 向量 + dense/sparse 可组合；服务端 `FusionQuery` RRF 固定 k=2（不满足 k 注入需求，已改客户端融合）；sparse 参数可开 `Modifier.IDF`（**当前未开**，`docs/核心算法.md` §1） | payload 过滤（当前未用；`query_hybrid` 拆成两路独立查询后**过滤需每路重复下推**，`database/qdrant.py` 已注明） | 低：单二进制绿色安装，启停脚本编排 | 亿级（官方口径，本仓未压测，待实测） | 高：`QdrantRepo` 封装、声明三路/实写两路（dense+sparse_bm25）、评测、灾备全链路已建成 |
| pgvector | `sparsevec`（0.7+，HNSW 索引支持稀疏）+ `halfvec`；hybrid = dense+sparse 两路自行融合；`hnsw.iterative_scan` 解决「过滤后漏召回」 | SQL WHERE（与业务查询同库同事务，能力最强） | 低增量：复用现有 PostgreSQL（业务库已在栈内） | 百万–千万级经验区（待实测） | 中：PG 已在栈内，但三路 Named Vectors → 表结构重设计，`QdrantRepo`/RRF/灾备/评测全链路重写 |
| Milvus | 2.5 起服务端 BM25 全文检索（**服务端自动分词**）+ 原生 sparse + 服务端 hybrid 融合 | scalar 过滤 + 服务端融合 | 高：standalone 也自带元数据/存储组件；**绿色安装（官方 zip 落 services/）路线不存在**，与拷问决策 #1 冲突 | 十亿级 | 低：部署形态、客户端、写入管道全部重做 |
| Chroma | 2025 起支持 sparse vector search（schema 配置 + RRF hybrid，[官方公告](https://www.trychroma.com/project/sparse-vector-search) 已核实；但该能力在 [Cloud 文档](https://docs.trychroma.com/cloud/schema/sparse-vector-search)下呈现，**OSS 单机版可用性待核实**） | 元数据过滤；对比引文称无 payload 索引（待核实） | 低：轻量单机 | 中小规模 | 中：需换客户端与仓库层；灾备双写、幂等 upsert、payload 校验全部重接 |

**保留 Qdrant 的理由**（除 §1 三条结构性理由外）：
1. k 可注入的客户端 RRF、声明三路/实写两路（dense+sparse_bm25）的双写、`Chunk.id` 内容确定性幂等、灾备通道——检索域全部
   已建成且有测试护航；迁移收益在当前规模下为零。
2. 运维约束（绿色安装、删目录=卸载）只有 Qdrant 与 Chroma 满足；Chroma 的 sparse 支持
   在 OSS 版上待核实且成熟度存疑。
3. 低成本改进路线存在：BM25 通道开 IDF（`SparseVectorParams(modifier=Modifier.IDF)`）
   只是**集合级参数**，走版本化集合切换即可，无需换库（是否值得做见 §5 O6，先实测）。

**迁移触发条件**（出现任一条才重新启动选型，否则不动）：
- **T1 规模**：语料到千万级点，或过滤型向量查询并发显著上升（当前均无）。
- **T2 一致性**：业务明细（PG）与知识检索需要同事务强一致（pgvector 路线的唯一决定性理由）。
- **T3 服务端 BM25**：需要服务端分词/IDF/全文检索且不愿维护 jieba 通道（Milvus 2.5；
  前提是接受其运维形态改变）。
- **T4 资源**：单机内存/磁盘瓶颈出现（`on_disk_payload` 已开，还有 quantization 未启用的余量）。

## 4. 评测协议（可执行）

> 前置红线：**付费调用前先向用户报价确认**（AGENTS 预算红线；`JUDGE_*` 槽位不参与 retrieval
> 模式——该模式零 LLM 零判分，`eval/retrieval_eval.py` 已按此实现）。**语料到位前（75 向量）
> 结论不外推**；快照自带 `corpus_note` 与 embedding 指纹，跨批次可比性由快照保证。

**Step 0 语料 ingest**（免费部分先行）
1. 原始 FAQ xlsx 恢复进 `data/raw/`（当前为空，交接文档 §3）；法规全文按决策 #12 整理。
2. `cd backend && uv run bidqa ingest knowledge --input <xlsx>`（嵌入 API 付费 → **先报价确认**；
   F3 摘要走廉价槽位，成本估算唯一入口 `enhance_split.estimate_cost`：块数×600 输入 + 块数×100 输出 token）。
3. 入库后**必须复查检索 mode**：`--mode smoke` 观察 `mode=hybrid` 而非 `bm25_fallback`
   （灾备通道教训：嵌入不可用时会只写 `sparse_bm25`，此后 hybrid 恒空，`docs/核心算法.md` §1）。

**Step 1 基线**
```bash
cd backend && uv run bidqa eval --golden ../eval/golden/rag_v0.jsonl --mode retrieval
```
产出 recall@5/10、MRR、nDCG@5/10 逐题 + 均值快照（`backend/eval/results/`，命名含日期/git/judge 指纹）。
**golden 现状（本仓核实）**：`rag_v0.jsonl` 8 题全带 `ref_sources`；`agent_v0.jsonl` 40 行中仅 4 题带
非空 `ref_sources`——语料扩充时**golden 必须同步重生成**（`ref_sources` 存 `Chunk.id = uuid5(source_type|title|text)`，
切分或文本一变 id 即变，见 §5 O4 风险）。

**Step 2 替换 embedding 实现（factory 注入，不改调用方）**
- 注入点唯一：`rag/factory.py: build_embedding()`（返回实现 `embed_query`/`embed_documents`
  同接口的 Client；`Retriever` 只依赖该接口）。候选实现：新建 Client 类或改 `EMBEDDING_*` 三配置项
  直接指向新端点/新模型（OpenAI-compatible `/embeddings` 协议一致时零代码改动；无稀疏返回时
  `sparse_embedding` 缺省 → 客户端已按 None 降级，行为符合现有降级语义）。
- 集合按 `docs/01` §4.1 版本化：建 `bidqa_knowledge_v2` → `QDRANT_COLLECTION` 切换 →
  全量重 ingest → 原子切换 → 删旧。**禁止原地清空重建**。

**Step 3 同口径对比（变量唯一化）**
- 同 golden、同 `ks=(5,10)`、同语料快照、同 `top_k=max(ks)=10` 检索窗口；每候选一轮快照。
- 若候选无学习稀疏（§2 结构性结论）：候选侧 hybrid = dense + sparse_bm25，报告单列一行声明
  「稀疏通道差异」，不算作 embedding 单变量。
- 记录五组数：recall@5/10、MRR、nDCG@5/10（快照已有）+ 检索延迟 P95（调用侧计时，勿读
  `RetrievalResult.elapsed_ms` 缓存旧值——`rag/retrieve.py` 类 docstring 口径）+ 成本
  （ingest token 数 × 单价 + 查询侧每次调用 token 数）。
- 判定门槛（建议，跑批前可调）：recall@5 不低于基线 -2 个百分点、P95 ≤1.5s（`docs/02 §0.1`
  既有验收线）、全量重 ingest 成本 ≤ 报价确认额度。任一不满足 → 保留 bge-m3。

**Step 4 结论登记**：结果写入本文档 §2 表格的「待实测」位（数字 + 快照文件名），并同步
`docs/AI交接文档.md`；`.env` 改动（若切模型）走配置三列表流程（`docs/01` §5）。

## 5. 链路优化清单

> 每项 = 假设 / 改哪个参数或环节 / 观测指标 / 风险。**全部依赖真实语料 + 付费跑批（报价确认后）**，
> 本轮只登记方案与验收口径，不动任何参数。参数现值以 `docs/01` §4.1 检索参数表为单一来源。

| # | 项 | 假设 | 改哪里 | 观测指标 | 风险 |
|---|---|---|---|---|---|
| O1 | RRF k 分档 | 现值 keyword 30 / mixed 60 / concept 90 是设计拍定值；概念型问题可能需要更平滑的排名融合（更大 k），关键词型反之 | `rag/classify.py:_RRF_K`（分类词表 `rag/keywords.yaml` 不动，先只调 k） | 分档切片的 recall@5/10、nDCG@5（按 classify 输出分桶对比）；P95 | 词表覆盖不足时分类错档，调 k 反而放大错档；k 影响全部问题，需分桶归因 |

## 6. 风险与开放问题

- **R1 许可证**：jina-embeddings-v3 权重 CC-BY-NC（非商用，商用需签协议，§2 已核实）——
  本项目含甲方验收，纯自托管路线即不可行；OpenAI 候选受其商用条款约束。bge-m3（MIT）、
  Qwen3（Apache-2.0）、gte-Qwen2（Apache-2.0）已核实无此问题。
- **R2 数据出境**：OpenAI 候选 = 招投标语料（含企业中标明细、采购人信息）出境处理；
  练习版可评估，甲方生产环境默认排除。待与用户确认语料敏感性分级。
- **R3 SiliconFlow 单点依赖**：嵌入与重排同一家供应商，同源故障时灾备只有 BM25 单路
  （无 rerank、无 CRAG 可比分数、`mode=bm25_fallback` 如实降级）。开放问题：是否引入
  第二家 embedding 供应商做**主备切换**——注意这与拷问决策 #4「不引入第二家嵌入 API」
  的边界：该决策指的是灾备**不**走第二家 API（灾备=本地 BM25）；换供应商属于选型替换
  （§4 协议范畴），不属于决策 #4 禁止的「并行第二路」。此边界需用户拍板后才动。
- **R4 75 向量结论无效性**（三重独立理由）：① HNSW 未建（75 < `indexing_threshold=10000`），
  延迟全为全扫量级，不可外推；② 语料仅 FAQ，法规/流程/招标文件覆盖度为 0，
  `source_type` 维度的结论（如法规类召回）根本无法产生；③ 存量 75 向量为旧编码口径，
  与现行 `encode_text` 混用。重新 ingest 后**所有**检索基线必须重测（`CORPUS_NOTE` 已落档）。
- **R5 golden 与语料联动漂移**：`Chunk.id` 内容确定性是把双刃剑——幂等入库依赖它，
  但切分/摘要/文本任何变更都使 golden `ref_sources` 失效。开放问题：语料扩充时 golden
  重生成的流程与责任人（人工确认期望来源，不可自动外推）。
- **R6 成本**：SiliconFlow `BAAI/bge-m3` 当前免费档（已核实存在免费模型页，实时政策
  **待核实**——免费档可能限流或调整）；全量重 ingest 的嵌入 token 成本、rerank 计价口径
  均待核实。任何跑批前按 AGENTS 红线向用户报价确认。
- **R7 429 行为**：嵌入/重排端点 429 不重试（仅 `token.sensenova.cn` 定向重试，AGENTS 红线
  /审计 P0-3 修复在案）——选型更换供应商时**不得**为新端点私自加全局 429 重试。
